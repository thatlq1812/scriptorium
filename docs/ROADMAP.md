## Light Design cluster render backend: SVG/Pillow → HTML/CSS + headless-browser (decided 2026-08-07, not yet built)

Owner raised a real pain point (`PROJECT.md`, 2026-08-07): the design team's promotional-content work in Canva is slow and hard to reuse, and asked for real research (not opinion) into whether an AI agent can design/edit like a human — posters, ads, job-listing snippets — standardized into an ideate→design→check→revise→repeat pipeline, since current tools seem to "blindly stack content onto the page."

**Research done** (papers + repos, not invented): the "blind stacking" read is accurate for the dominant older paradigm (LayoutGAN/LayoutVAE/CanvasVAE-era single-shot layout generation), but the 2025-2026 frontier is actively converging on exactly the iterate/critique/revise loop the owner described — `SheetDesigner` (arXiv 2509.07473, Apache/CC-BY-4.0, real rule+vision reflection loop, though for spreadsheets not posters), `PSDesigner` (arXiv 2603.25738, tool-calling agent operating real PSD files), `BannerAgency` (arXiv 2503.11060, MLLM multi-agent banner-ad design, deliberately outputs editable Figma/SVG not static pixels), `COLE`/`OpenCOLE` (CyberAgentAILab, Apache-2.0, hierarchical intention→JSON→render pipeline). The field's own honest admission (2026 benchmark papers `Graphic-Design-Bench`, `AesEval-Bench`, `TASTE`): the "check" step is the genuinely unsolved part, since design has no single objectively-correct answer the way object recognition does — VLM-as-aesthetic-judge is itself an open research question, not a solved capability to plug in.

**Real experiment run this session** (not just cited papers): built a real, deliberately-imperfect poster via `svg-poster-builder`+`poster-generator` (Vietnamese coffee-shop poster, V1), looked at the actual rendered PNG with real vision, found the title text was 100% invisible (declared color == the background color it composited over — a compositing bug NO mechanical validator in this registry can catch, since `brand-identity-linter`/`svg-poster-builder` only check declared values, never what actually renders on top of what). Fixed via 2 real critique→revise rounds (V2 introduced a NEW real bug — 2-line wrapped title text overflowing its own zone height into the subtitle below, from the renderer's manual `font_size_pct`-of-fixed-zone-height math — fixed in V3 by recomputing the safe font-size ceiling). Confirms the ideate→design→check→revise loop is real and works with tools already in this registry; also confirms the 2 defect classes are NOT the same kind — the invisible-title bug is genuinely vision-only, the overflow bug is a script-math bug a smarter deterministic pre-check could plausibly catch on its own (worth building before reaching for a vision call every time — matches this project's "deterministic-first" discipline).

**SVG vs HTML decision**: owner asked directly, favoring HTML/CSS for agent-friendliness + the icon/decoration-repo ecosystem (mostly ships as standalone SVG files, which embed far more easily into HTML `<img>`/inline-`<svg>` than into a second parent SVG's own viewBox/namespace). Investigated Canva's own real rendering approach first (per owner's explicit ask): Canva does NOT use plain DOM/HTML layout — it's a custom WebGL/HTML5-Canvas engine with its own GPU-based alpha-blending/compositing pipeline (`canva.dev/blog/engineering/alpha-blending-and-webgl`), i.e. neither "SVG" nor "HTML" as commonly meant — a full canvas rendering engine is out of reasonable scope for a deterministic, no-AI-backend, narrow-scope project like Scriptorium, so "do what Canva does" doesn't actually resolve to "use HTML." Narrowing to the real remaining choice (SVG-XML-generation vs. HTML/CSS+headless-browser), ran a direct empirical A/B: rebuilt the exact V1 poster content as HTML/CSS with a `flex` column layout and a naively-guessed title font-size (same category of guess that caused the SVG version's overflow bug) — the flexbox layout auto-sized around the wrapped text via `gap`, with zero manual height math and no overlap, on the first attempt. One real technical gotcha found and solved along the way: CSS `mm` units are always defined relative to 96 CSS-px/inch regardless of requested viewport size — a print-accurate render needs the viewport sized at the true 96dpi-equivalent pixel count first, then upscaled via `device_scale_factor` for higher output resolution, not sized directly at an arbitrary target DPI.

**Decision**: migrate the Light Design/media render backend from SVG-string-generation (`svg-poster-builder/scripts/render_layout.py`) + Pillow-based compositing (`poster-generator/scripts/render_poster.py`) to HTML/CSS rendered via headless Chromium (Playwright — already installed and audited in this repo via `browser-web-renderer`, not a new dependency category, just a new use of an existing one: local-file rendering instead of only remote-URL text extraction). The `layout.json`/`content.json` schema/contract the calling agent already writes to stays unchanged — only the rendering internals swap. Deliberately did NOT adopt TypeScript alongside this (owner asked): TS is a language-level type-safety tool relevant only if the render layer became a JS/TS component system (e.g. React), which is a separate, much heavier architectural jump (first-ever Node/npm toolchain dependency in this all-Python registry) that solves a problem this project doesn't have yet — the exact same HTML/CSS output is emittable from a plain Python string-templating script, the same shape `render_layout.py` already uses for SVG today, with zero new toolchain.
