# legal-web-search

A protocol, not a lookup service. This skill never searches anything itself and holds no API key — the calling agent does the actual web search/fetch with its own tools (same relationship `deep-research` has to research generally). What this skill supplies: a domain allowlist mimicking where a lawyer would actually look, mandatory "as displayed by the source" framing for any hiệu lực-like status (never asserted as this skill's own fact), and a validator that catches an undisciplined search record before it's trusted.

## Why this scope, and why NOT a lookup chatbot

The original proposal for this skill (from another agent's `request.md`, reviewed 2026-07-27) was to scrape `thuvienphapluat.vn`/`luatvietnam.vn`/`vanban.chinhphu.vn` and directly assert a document's hiệu lực (in-effect) status. That is functionally the "legal-lookup chatbot" `docs/specs/STRATEGY_SPEC.md` §2 explicitly lists as a non-goal ("the Vietnamese market is already crowded... Scriptorium positions at the meta layer") — and it repeats the exact fabrication risk `legal-citation-checker` and `document-ai-structurer` already declined: no free, official Vietnamese legal-document API exists, and a commercial site's displayed status can be stale or wrong without any way for this project to detect it.

The owner's actual intent, clarified during review, was narrower and legitimate: give the calling agent a **disciplined search process** — prioritize official sources, note how recent a result is, never treat one source as settled truth — the way an actual lawyer searches, not a chatbot answering "is this law still valid?" This skill implements exactly that discipline and nothing more: it validates that a search record stayed within an allowlist, is dated, discloses status as "what the page said" rather than asserting it, and surfaces (never silently drops) a disagreement between sources.

## Protocol (followed by the calling agent, not by any script here)

1. **Search only allowlisted domains** (`references/allowed_domains.json`) — government sources (`vanban.chinhphu.vn`, `chinhphu.vn`, `dichvucong.gov.vn`, `moj.gov.vn`) tiered `primary`; commercial legal databases (`thuvienphapluat.vn`, `luatvietnam.vn`) tiered `secondary`, useful for triangulation but never more authoritative than a primary source when they disagree.
2. **Prefer the most recent result** when multiple versions of the same document exist — an amended/replaced document should be found over a repealed one, but note the date you found it, don't assume it's still current by the time it's used.
3. **Record every result's URL, title, and the date you accessed it** — not retroactively from memory.
4. **If a page displays a hiệu lực-like status, record it as `as_displayed_status: {"text": "...", "as_of": "..."}` verbatim** — exactly what the page said, never rewritten as this skill's own assertion.
5. **If two sources disagree on the same document's status, say so explicitly** in `contradiction_notes` — never silently pick one.
6. **Set `caveat_acknowledged: true`** only once you understand this record is not a hiệu lực determination.
6b. **If a direct fetch on an allowlisted URL returns only a JS-rendered shell** (confirmed real for `dichvucong.gov.vn` procedure/form pages — see Known limitations), you may still record a result from a WebSearch summary instead of a literal page quote, but must set `"js_shell_detected": true` and `"snippet_note"` (non-empty, disclosing what was actually obtained and how) — never silently present snippet-derived content as if it were a direct quote. This is a short-term mitigation (owner decision, 2026-07-27); the long-term fix is browser automation to render the DOM first, tracked as a backlog item, not built here.
7. **Validate before trusting the record**:
   ```bash
   python skills/legal-web-search/scripts/validate_search_record.py record.json
   ```
   Exit 0 = every result is on an allowlisted domain, dated, self-consistent. Exit 1 = errors (each naming the exact result/field and reason). Exit 2 = malformed input.

Start from `assets/search_record_template.json` for the exact schema.

## What this skill does NOT do

- Does not search anything itself — zero network calls in `validate_search_record.py`.
- Does not determine or assert a document's real-world hiệu lực status — only that a *displayed* status was recorded honestly and with its source. A human/agent must still exercise judgment about what to do with a disagreement.
- Does not expand the allowlist automatically — adding a domain to `references/allowed_domains.json` is a deliberate, reviewable edit, never inferred from what a search engine happened to return.
- Does not call any LLM/AI API — Scriptorium never does (`docs/specs/STRATEGY_SPEC.md` §2/§6/§7.4); this is a protocol + validator only, same shape as `deep-research`.

## Backlog (not built, deliberately deferred)

- ~~Browser automation for JS-rendered public-service portals~~ — **built** (`browser-web-renderer`, 2026-07-27) and tested for real against `dichvucong.gov.vn`. Result: NOT the fix hoped for. The site WAF-blocks a real headless browser on every page tested (including the bare homepage, a "Request Rejected" response) — this was never a JS-rendering problem alone, it's bot-detection at the network layer. `browser-web-renderer` deliberately does not attempt to evade a WAF (see that skill's "What this skill does NOT do"), so this specific site's Item 4 gap is now understood to be **harder than originally scoped**, not solved by rendering. `browser-web-renderer` DID work well against `vanban.chinhphu.vn` (richer extraction than a plain fetch, found a real attached PDF link) — useful for other sites, just not this one.

## Known limitations (v0.2.0, not yet through official quality-eval)

- The allowlist is small and Vietnam-specific (4 primary, 2 secondary domains) — deliberately conservative rather than broad; a real use case needing another domain should add it explicitly, not work around the check.
- Domain matching is exact-or-subdomain only (`urlparse().hostname`), no protection against a URL that's technically on an allowlisted domain but at a path that isn't actually the legal-document section of that site (e.g. a forum post on a news subdomain) — the allowlist controls the domain, not the specific page's relevance.
- Contradiction detection only fires when 2+ results share the same `document_ref` string exactly — a typo'd or differently-formatted số hiệu across 2 results won't be recognized as the same document.
- **`dichvucong.gov.vn` procedure/form pages are not reliably fetchable, and now confirmed not solvable by rendering alone** — a plain fetch gets a JS shell; a real headless browser (`browser-web-renderer`, tested 2026-07-27) gets a WAF "Request Rejected" block instead, on every page tried including the homepage. This is the site the original Item 4 (form suggestion) proposal depended on most, and this project does not attempt to evade a WAF. v0.2.0's `js_shell_detected`/`snippet_note` fields let a WebSearch-summary-level result still pass validation, honestly flagged — that remains the practical ceiling for this site, not a placeholder for a future fix. Item 4 stays an Open Gap (owner decision). See `legal-form-filler/SKILL.md` for how this affects that skill's scope, and `browser-web-renderer/SKILL.md` for the full real-testing detail.
- **`thuvienphapluat.vn` blocks direct WebFetch** (HTTP 403) — usable only through WebSearch's own summarized snippets, which don't give a literal quotable status string the way this skill's `as_displayed_status.text` field wants. Triangulating a primary-vs-secondary hiệu lực disagreement (the scenario `contradiction_notes` exists for) is harder in practice than the fixture-only testing suggested.
- `vanban.chinhphu.vn` was the one source that fetched cleanly and produced a real, usable record — good for statute lookup/citation grounding (Items 1, 2, 10, 11 territory), not yet proven for form-suggestion (Item 4).
- Hasn't passed stage 4 (quality eval, ≥2 harnesses) or stage 5 (security audit — self-audited only this session: stdlib-only, no eval/exec/subprocess/os.system/network calls found).
