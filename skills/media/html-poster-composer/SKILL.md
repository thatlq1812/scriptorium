# html-poster-composer

Same zone-based layout.json/content.json contract svg-poster-builder/poster-generator used -- only the render engine changed, from SVG-string-generation + Pillow-compositing to real HTML/CSS rendered by headless Chromium. A caller who already has a working layout.json/content.json from the superseded skills needs zero changes to use this one.

## Why this skill, and why the migration

Owner-directed research (`PROJECT.md`, 2026-08-07): design-team promotional work in Canva is slow and hard to reuse; asked for real research into an agent-driven ideate→design→check→revise pipeline. A real experiment that session (see `docs/ROADMAP.md`) found a genuine bug the old Pillow renderer couldn't self-detect: a title's declared color exactly matched its background (invisible text, a compositing issue only vision catches), and fixing it introduced a SECOND real bug -- the same title, now 2 lines, silently overflowed its own zone into the subtitle below, because the renderer computed a font size from a fixed formula and just drew it with no check. That second bug class -- script math getting a size estimate wrong with no verification -- is exactly what HTML/CSS's real layout+measurement engine is better at than a hand-rolled Python formula. Owner directed the technology migration; Canva's own real engine (WebGL/Canvas, investigated directly per owner's request) turned out to be neither SVG nor plain HTML, ruling out "copy Canva" as the actual answer and narrowing the real decision to SVG-generation vs. HTML/CSS+headless-browser.

## Run

### Preview (layout only, no content needed)

```bash
python scripts/compose.py <layout.json> -o preview.png --preview
```

Renders every zone as a labeled, colored placeholder rectangle (same idea svg-poster-builder v0.3.0 had) plus a legend below the canvas (id/type/fill-swatch/declared `text_label`) -- a quick sanity check of composition before real content exists.

### Final render (real content)

```bash
python scripts/compose.py <layout.json> <content.json> -o poster.png --pdf poster.pdf
```

`--pdf` is optional; omit it for a PNG-only render. Both re-validate layout + content before touching pixels (same `_validate_layout`-equivalent + `validate_content` rules as the superseded skills). Real content types: `fill` (solid color), `image` (`path` + `fit: cover|contain`, via CSS `object-fit` -- never distorts, only crops or letterboxes), `text` (`text`/`color`/`align`/`font_size_pct`/optional `font_family`, only valid on `typography_frame` zones).

### Font embedding (v0.1.1)

`content.json` may declare an optional top-level `"fonts": {"FamilyName": "path/to/font.ttf|otf|woff|woff2"}` -- each declared font is base64-embedded directly into the rendered HTML's `@font-face` (no external font request, output is byte-identical regardless of what's installed on the rendering machine). A `text` entry references one via `"font_family": "FamilyName"` -- refused at validation time if that family isn't declared, or if the font file doesn't exist / isn't a real parseable font (checked via `fontTools`, catching a corrupt/renamed-non-font file loudly instead of an inscrutable browser failure). ONE complete font file per family -- the real pattern this was elicited from (see `metadata.elicited_from`) embeds one full-coverage file, not a split latin/vietnamese-subset pair.

### Anchor-relative zone positioning (v0.1.2)

A zone may declare `"relative_to": "<other_zone_id>"` + `"anchor"` (same 7-value vocabulary as `light-logo-arranger`'s `compute_anchor.py`: `top-left`/`top-right`/`top-center`/`bottom-left`/`bottom-right`/`bottom-center`/`center`) + optional `"gap_pct"` (default 0) INSTEAD OF `x_pct`/`y_pct` -- its position is computed relative to the referenced zone's corner/edge, offset outward by `gap_pct` (or overlapping inward if `gap_pct` is negative -- a real, deliberately-supported case, see `metadata.elicited_from`). `relative_to` must reference an EARLIER zone in the same `zones` list that already has a resolved position (no forward references, no self-reference, no dependency-graph solving -- single deterministic left-to-right pass). Still requires numeric `w_pct`/`h_pct` (size is always explicit); `x_pct`/`y_pct` and `relative_to`/`anchor` are mutually exclusive on the same zone. Resolved positions go through the exact same overflow/duplicate/coverage checks as hand-declared ones -- a relative zone that resolves off-canvas is refused exactly like a hand-authored one would be.

### Circular seal/badge (v0.2.0, a genuinely different shape)

```bash
python scripts/compose_seal.py <seal.json> -o seal.png [--pdf seal.pdf]
```

Rectangular percentage-zones don't fit a circular seal/badge composition (ring border + text curved along an arc + a center image) -- elicited directly from a real logo deliverable (`D:/elix/projects/temp_project_20260728/design/logo/logo-seal.svg`, a real 25-`<path>` circular seal, see `metadata.elicited_from`). This is the one place this skill still generates real SVG (not HTML/CSS zones) -- curved text needs `<textPath>` along a real arc, which CSS has no native equivalent for; the SVG is then wrapped in HTML and rendered through the same Playwright PNG/PDF pipeline as everything else in this skill.

`seal.json` schema: `diameter_mm` (required), optional `background_color` (hex), optional `fonts` (same shape as the main render mode's top-level `fonts`), optional `rings` (list of `{radius_pct, stroke_color, stroke_width_pct}`), optional `arc_text` (list of `{text, radius_pct, start_deg, end_deg, color, font_family?, font_size_pct?, letter_spacing_pct?}` -- angles in degrees, standard math convention with `0`=3-o'clock/right, `90`=6-o'clock/bottom, increasing clockwise; text is always centered on the declared arc via `startOffset="50%"` + `text-anchor="middle"`, not left-anchored, so `start_deg`/`end_deg` only need to bound the available arc, not predict exact text length), optional `center_image` (`{path, radius_pct}`, clipped to a circle via CSS `object-fit`-equivalent SVG clip-path).

**Real bug found and fixed while building this**: text placed along the bottom half of the circle rendered upside-down/mirrored -- a well-known SVG `textPath` quirk (a path's glyphs orient "up" relative to the path's OWN direction of travel, and a naive always-clockwise arc reads correctly on top but backwards on bottom). Fixed by auto-detecting the arc's midpoint and reversing the underlying path's direction (same visual arc, opposite endpoint order + opposite sweep flag) whenever the midpoint sits in the bottom half -- the caller never has to think about this, `start_deg`/`end_deg` always mean "the arc spanning these two angles," oriented for upright reading automatically.

### Multi-page batch mode (v0.3.0, general-purpose -- not tied to any content domain)

```bash
python scripts/compose_batch.py <layout.json> <pages.json> -o out_dir [--pdf combined.pdf] [--format png|jpg]
```

For turning any long-form structured content with a repeating unit (report sections, catalog entries, a step-by-step explainer -- deliberately domain-agnostic, owner directive 2026-08-07) into a visually-consistent set of information pages: ONE `layout.json` template, filled with different content per page, rendered as numbered `page_01.png`/`page_02.png`/... (or `.jpg`) plus an optional single combined multi-page vector PDF (`prefer_css_page_size=True` + a CSS `@page` rule, not N separately-merged PDFs). `pages.json` = `{"fonts": {..., shared across every page, embedded ONCE not per-page}, "pages": [{"zones": {...same shape as a single content.json's zones...}}, ...]}`. Every page is validated against the same `layout.json` (via the same `validate_content()` every other mode uses) before anything renders -- every failing page+zone reported, not just the first. The auto-fit loop runs across all pages' zones in one pass (each element still measured against its own zone independently, `relative_to`/`anchor` positions resolved once and reused identically on every page since the layout is shared).

**Real bug found and fixed while building this** (not batch-specific, but only actually triggered by dense real body-text content batch mode's own testing used): `.text-content`'s fit-check only ever measured HEIGHT, trusting `width:100%` + word-wrap to guarantee no line exceeds the zone's width -- true for normal text, but a single unbroken long token (no whitespace to wrap at) doesn't wrap at all by default, so it silently overflowed the canvas edge sideways (content clipped, zero warning) while still measuring as one short line, sailing past the height-only check. Fixed by adding `overflow-wrap:break-word` to the shared zone CSS (`compose.py`'s `ZONE_BASE_CSS`, now imported by both `compose.py` and `compose_batch.py` instead of two copies drifting) -- verified real with an extreme adversarial case (6,000 unbroken characters) correctly refusing on both the single-page AND batch paths, and confirmed a merely-large-but-genuinely-fittable case (800 unbroken characters in a tall zone) correctly renders instead of over-refusing.

### Video-frame canvas + transparent PNGs (v0.4.0)

`"canvas": {"preset": "VIDEO_HD"}` renders at 1920x1080 instead of a print size — for a video intro/outro card, or a full-frame image meant to be `overlay`-composited onto footage by another tool (e.g. `video-assembly-composer`'s `watermark_image`). Pair with content.json's top-level `"transparent_background": true` for the overlay case: the canvas renders with a real alpha channel (no `#fff`/opaque fill) instead of the default opaque-white background, so only the zones you actually declare (e.g. 2 small `typography_frame` text zones) are visible when composited over other video. Omit `transparent_background` (or set it `false`) for an ordinary opaque card, e.g. a title/credits intro/outro slide.

### Auto-fit (the real fix this migration exists for)

Every `text` zone's font size starts from `font_size_pct` (same meaning as before -- % of the zone's own height) then gets measured for real: the actual rendered text-block height (via Playwright's `bounding_box()`, the browser's own layout engine, not an approximation) is compared against the zone's real pixel height. If it overflows, the font shrinks by a fixed factor and gets re-measured, up to 14 attempts or an 8px floor. If nothing in that range fits, the WHOLE render is refused (exit 1, naming every zone that couldn't fit and by how much) -- no file is written. This is strictly stricter than the old Pillow renderer, which silently overflowed with zero warning; a caller who wants a smaller layout to fit must actually enlarge the zone or shorten the content, not just tolerate a hidden defect.

## What this skill does NOT do

- Does not judge design quality, color contrast, or visual hierarchy -- it guarantees text fits its declared zone (a mechanical fact), never that the poster looks good (a judgment call). A title exactly matching its background color still renders (correctly, per the declared values) as invisible -- that's a content/color choice bug, not a layout bug, and this skill won't catch it. Pair with real vision review (look at the actual PNG) for that class of defect.
- Does not generate imagery -- `image`-type content needs a real file path (from `gemini-generator` or elsewhere); no AI call anywhere in this skill.
- Does not support arbitrary canvas sizes -- same 2 ISO 216 presets (A1, A4) the superseded skills had.
- Does not embed or bundle any icon/decoration library -- a caller wanting to composite icons uses `image`-type zones pointing at real icon files; adopting a specific icon pack requires running `license-compliance-check` on it first, not assumed free-to-use.
- Does not do any automated Vietnamese-glyph-coverage check on an embedded font -- tried this for real (a cmap-based check) and found it produces a false refusal on a font already proven correct in production (see `font_embed.py`'s own docstring for the full finding); verify by rendering real sample text and looking, same discipline as the real elicitation source's own `render_preview.py` + human review. Pair with `light-logo-arranger`'s `resolve_font_fallback.py` for SYSTEM-font pairing safety (a different, narrower question -- is a non-embedded font available on the rendering machine).

## Known limitations (v0.4.0)

- Canvas sizes are still a fixed preset set (`A1`/`A4`/`VIDEO_HD`), not arbitrary caller-declared pixel/mm dimensions -- a 4th real use case would need its own named preset added to `CANVAS_PRESETS_MM`, not a general "any size" escape hatch.
- `transparent_background` is all-or-nothing for the whole canvas -- there's no per-zone transparency (e.g. one zone opaque, another transparent on the same render).
- `poster-generator`'s optional Gemini-powered `suggest_layout.py` (auto-proposing zone placement from a caller-declared element list) was deliberately NOT ported this round -- a real, flagged follow-up, not silently dropped. Layouts must be hand-authored or otherwise sourced for now.
- The auto-fit loop only handles font-size-vs-declared-height mismatches for `typography_frame` zones -- it does not resize or reposition zones themselves, and does not attempt to auto-balance whitespace across the whole canvas.
- `image`-type zones use CSS `object-fit` (`cover`/`contain`) -- no auto-crop-to-focal-point or smart cropping; a caller needing that judgment should pre-crop the source image.
- Preview mode's per-zone inline label can visually clip on a very small zone (e.g. a narrow `decorative_element`) -- the legend below the canvas is the authoritative fallback for exact zone identity, same discipline `svg-poster-builder` v0.3.0 established.
- `resolve_zone_positions()`'s single left-to-right pass means a `relative_to` chain can only point backward -- no forward references and no automatic reordering, by design (keeps resolution deterministic and simple; a caller wanting zone B positioned relative to zone A must declare A first).
- `compose_seal.py` supports exactly one `center_image` per seal (no multi-layer center composition) and doesn't auto-balance multiple `arc_text` entries' radii/spacing against each other -- each is positioned independently from its own declared `radius_pct`/angles, a caller's job to keep them from colliding.
- `compose_batch.py` requires every page to declare the SAME set of zone ids (the shared `layout.json`) -- a page can't skip or add a zone; a caller wanting an occasional different layout needs a separate batch run with its own `layout.json`, not a mixed batch.
- `compose_batch.py` has no per-page override for `layout.json` itself (e.g. a slightly different accent color per page beyond what `content.json`'s per-zone fields already allow) -- true per-page layout variation is out of scope, this is for N pages that are genuinely the same template.
