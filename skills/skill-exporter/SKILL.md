# skill-exporter

Packages skills for someone outside this repo. The distribution half of the pipeline — everything else in Scriptorium creates/audits/catalogs skills; this is the only skill whose job is to hand a finished bundle to somebody else.

## Suggested intake (not a fixed script — the calling agent's own judgment drives this)

There is no mandated question sequence — the owner was explicit that this depends on the calling agent's own intelligence, not something this skill can script. A reasonable starting checklist, useful as a baseline rather than a requirement:

1. **Who is this for?** (the user themselves, a colleague, a friend, another project) — informs tone/scope, not a registry filter by itself.
2. **What task/workflow?** — map to `task_type` (`research`/`document-conversion`/`drafting`/`review-qa`/`coordination`) and, if it's clearly domain-specific (legal, education...), to `domain`.
3. **Any specific skills already known/wanted by name?** — pass directly to `export_bundle.py`, skip the filtering step.
4. **Anything explicitly out of scope?** — narrow with `--object-type` or just hand-pick from the candidate list rather than exporting everything that matched.

## List candidates

```bash
python skills/skill-exporter/scripts/list_candidates.py --domain legal --task-type review-qa [-o candidates.json]
```

Filters are OR-within-axis (`--domain legal general` matches either), AND-across-axis. Always hard-excludes any skill with `license_debt` set or `security_audit.status != "passed"` — printed separately to stderr, never silently dropped without explanation.

## Export a bundle

```bash
python skills/skill-exporter/scripts/export_bundle.py <skill_id> [<skill_id> ...] -o bundle.zip \
    --for "short description of who/what this is for" \
    [--exclude domain:education] [--exclude some-skill-id] [--force]

# Or export everything that passes the gate (replaces manually zipping skills/+registry/):
python skills/skill-exporter/scripts/export_bundle.py --all -o bundle.zip \
    --for "short description" [--exclude domain:education] [--force]
```

Auto-resolves dependencies recursively: if a requested skill's registry `dependencies` field names another skill_id (not a package pin), that skill is pulled in too, and so on. `--exclude` (repeatable) removes a skill by exact `skill_id` or by `axis:value` tag pattern (e.g. `domain:education`, `task_type:drafting`) — for a Legal-only bundle that a broader query would otherwise pull education-tier skills into. If an exclusion would remove a skill still needed as a hard dependency of something staying in the bundle, the whole export is refused rather than shipping a bundle whose dependency chain is silently broken. `--all` cannot be combined with explicit `skill_id`s -- use `--exclude` to narrow it instead.

Every export writes 4 files at the zip root:
- **`START_HERE.md`** — an ordered first-run checklist: install the skills into your harness's own skill directory, bootstrap a shared Python venv if any bundled skill needs one, run `project-workspace-initializer`'s `init_workspace.py` if it's in the bundle, then delete `START_HERE.md` and the bundle's own `skills/` folder. Meant to be read once and thrown away, not kept as reference.
- **`MANIFEST.md`** — every included skill with version/tags/security_audit status and why it's here (`requested` or `dependency of <parent>`), the "Where to install"/"Python environment" per-harness detail `START_HERE.md` points back to, plus a note telling the consuming agent that chained skills in the bundle are meant to be used together for one task, not economized against a generic "minimize tool calls" instinct.
- **`dependency-tree.md`** — the same reasoning as its own file, structured as requested vs. auto-included.
- **`skills.lock`** — `skill_id -> {version, content_sha256}` for every included skill, a plain content hash (not a package-registry version pin, since skills have none) letting a later session verify this exact bundle's contents haven't drifted.

Exit 0 = exported. Exit 1 = a requested skill_id doesn't exist, fails the hard-exclusion rule, or an `--exclude` breaks a hard dependency (whole export refused, nothing written — not a partial bundle with the bad skill quietly dropped; `--all` instead silently skips a non-exportable skill rather than refusing, since nothing was named explicitly). Exit 2 = malformed registry, output path already exists without `--force`, or `--all` combined with explicit `skill_id`s / neither given.

## Verify a bundle's reproducibility

```bash
python skills/skill-exporter/scripts/verify_lock.py <skills.lock> [--skills-dir <path>]
```

Recomputes each locked skill's content hash against a target `skills/` directory (defaults to this repo's own) and reports any mismatch or missing skill. Exit 0 = every locked skill still matches, 1 = at least one mismatch/missing (named), 2 = malformed lock file.

## What this skill does NOT do

- Does not interview the user itself — that's the calling agent's job, using its own language capability (same division of labor as `deep-research`/`legal-web-search`).
- Does not call any LLM/AI API — Scriptorium never does; both scripts are stdlib-only, zero network.
- Does not editorialize about `quality_score` (owner decision, 2026-07-27) — the field is shown factually in `list_candidates.py`'s output like any other registry field, not flagged as a blocking caveat.
- Does not override the license_debt/security_audit hard exclusion for any reason — no `--force`-style flag exists for this specific check (unlike the unrelated output-overwrite `--force`).
- Does not vendor non-skill dependencies (Python packages, external tools) into the bundle — only lists them in `MANIFEST.md` for the recipient to install via their own `python-env-bootstrap`-equivalent.
- Does not resolve exclusion conflicts automatically — if `--exclude` breaks a hard dependency, it refuses and names the conflict; the caller decides whether to exclude the dependent skill too or drop the exclusion.
- `skills.lock`'s content hash is not a cryptographic integrity signature for distribution security — it's a plain SHA-256 over file contents for drift-detection (did this skill change since export), not tamper-proofing against a malicious actor.
- Does not ship a copy of `registry/skills.json` in the bundle, even with `--all` — `MANIFEST.md`/`dependency-tree.md` already cover what's included and why, without exposing internal metadata (audit notes, other skills' details) for skills that aren't in the bundle.
- `START_HERE.md`'s steps are generated from what's actually in the bundle (venv step only if a Python dependency exists, workspace-init step only if `project-workspace-initializer` is included) — it does not know about a target harness beyond what `MANIFEST.md`'s "Where to install" table already lists, and does not itself run any command.

## Known limitations (v0.2.0, not yet through official quality-eval)

- No skill in the registry currently has `license_debt` set (the debt ledger is empty as of this session) — that half of the hard-exclusion path was verified via direct function calls with synthetic data, not a real registry entry. The `operational_status.state == "paused"` half IS verified against a real entry (`socratic-concept-helper`, both in single-skill export refusal and `--all` skip behavior). Re-verify the `license_debt` half against a real excluded entry if/when one exists.
- Dependency resolution only follows the `dependencies` field's exact string match against `skill_id` — a dependency declared with a typo or version-qualified id (unlike this registry's convention) would be silently treated as a non-skill dependency instead of pulled in.
- No de-duplication warning if the same skill is reachable via 2 different requested skills' dependency chains — harmless (the zip write is idempotent per path within one run), just not flagged.
- `--exclude`'s tag-pattern matching only supports one axis:value pair per flag, exact match, OR-combined across multiple `--exclude` flags — no AND/wildcard/glob matching (e.g. `education/*` from the original discussion transcript's example is expressed here as `domain:education`, not a glob).
- Audience matching is still user+task-driven by the calling agent's own interview, not automated past domain/task_type/object_type tag filtering — the "User + Task + Environment" richer matching a discussion transcript suggested isn't a separate mechanism, it's still the calling agent's judgment feeding `list_candidates.py`'s existing filters.
- Hasn't passed stage 4 (quality eval, ≥2 harnesses) or stage 5 (security audit — self-audited only this session: stdlib-only, no eval/exec/subprocess/os.system/network calls found in either script).
