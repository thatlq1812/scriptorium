# slide-deck-composer

Clones a real, professionally-designed `.pptx` template's own slides and injects caller-supplied content into them via lxml XML surgery — the template's actual design (fonts, colors, layout geometry, decorative elements) survives untouched. This is deliberately **not** a from-scratch layout builder: an agent choosing "which shape at which coordinates" produces generic geometric "AI slop" with no real design DNA. This skill keeps the agent's job where it's actually strong — content-to-slot mapping, judgment on what to emphasize, which template best fits the deck's real content — and leaves visual design to a real designer's real template.

## Architecture decision: clone-and-inject, not build-from-scratch

Two approaches were evaluated against the source platform's ~90-file presentation engine (`D:/elix/archive/platform_archive/modules/presentation/`):

1. **Build-from-scratch** (`ooxml/layout_builder.py` + `shape_factory.py`) — rejected. Forces the agent to invent layout/design from raw coordinates with ~5 generic shape primitives.
2. **Clone-and-inject** (`pptx/compiler.py` + `pptx/slide_builder.py`) — **chosen**. Clone a real template slide, replace its text in place.

**A further deliberate simplification versus the source system**: the source's `SlideBuilder._add_slide()` clones an empty **Slide Layout** and fills placeholders by role name from a `TemplateManifest` (a declarative idx-mapping layer, `pptx/template_manifest.py`, 1071 lines). This skill instead clones a real, already-content-bearing **slide** (`slide_duplicator.duplicate_slide`, ported from `PPTXCompiler._duplicate_slide`) and runs `shape_roles`' heuristic scoring directly against its real shapes to decide which cloned shape is the title vs. body. **No `template_manifest.py`-equivalent placeholder-idx mapping layer exists in this skill, and that is intentional, not a gap**: a manifest's whole job is figuring out which placeholder idx on an *empty layout* plays which role — this skill never touches an empty layout, only a real slide whose shapes' actual size/position/font/paragraph-count are directly measurable, which is exactly what `shape_roles.score_title_shape`/`score_body_shape` already consume. Verified end-to-end against three real Slidesgo templates with wildly different layout structures (see "Verified") with zero placeholder-idx bugs — the scoring approach generalizes better across templates that don't share a common Slide Layout ordering, which real-world Slidesgo/Canva/Google-Slides templates never do.

## Architecture decision (v0.2.0): agent-driven slide selection over pure heuristics

v0.1.1's hands-on visual-review round (bugs #6-10) proved a structural point: automatic slide-classification heuristics are an arms race against every new template's idiosyncrasies (icon-grids, world-map infographics, color-palette meta-slides each fooled the geometry scoring in turn, one fix at a time). The actually-right fix isn't a smarter heuristic, it's removing the guess entirely for the cases that matter: `scripts/thumbnail_grid.py` renders every real template slide to a labeled grid image so the CALLING AGENT looks at it and decides, the same way a human designer would — then `compile_deck.py`'s optional `source_slide_idx` field lets that decision flow straight through, skipping `pick_source_slide_index`'s heuristic for that slide entirely. This matches this project's own stated philosophy this round (owner, verbatim): "với độ thông minh của agent hiện tại, việc cung cấp hạ tầng và bối cảnh là đủ, thêm nữa là thừa và lấy đi mất khả năng sáng tạo của agent" — a capable agent with good infrastructure and context needs exactly that, not another layer of scripted judgment calls on top. The automatic heuristic is NOT deprecated by this — it's demoted to what it always should have been: a legitimate lower-effort fallback for when a caller doesn't want to spend the extra round-trip, not the only path.

## BYOT (Bring Your Own Template) — hard constraint

The caller supplies a `.pptx` template file path they already have rights to use. This skill's own `scripts/`/`assets/` **never** bundle, reference, or hardcode any specific template file or filename (verified — see "Security & isolation self-check" below). Real Slidesgo `.pptx` files under `data/slidesgo_templates/` in this repo are **local test fixtures only**, used exclusively for this skill's own development/verification and never copied into the skill folder or referenced by path from any shipped script.

## Usage

**Read this section fully before writing any `content.json` — it exists specifically so an agent picking up this skill cold, with no other context, still does this in the right order.** The single most common mistake is writing content first and then bolting a `layout` value onto it after the fact. Do the reverse: know what each part of the deck IS before deciding how it's shown.

### Recommended workflow, in order

1. **Outline the deck's real content first, in plain prose/notes — no `layout`/`markdown` fields yet.** Break it into the natural sections/beats a human would use: an opening statement, a comparison, a sequence of steps, a standalone quote-worthy line, a closing. Do this BEFORE looking at the template at all — the content's own shape should drive the layout choice next, not the other way around.
2. **For each section, classify its SHAPE against the table below and pick a `layout` value.** This is a judgment call on what the content actually IS, not a preference:

   | The content is... | → `layout` |
   | --- | --- |
   | The deck's opening — a title + one short framing line | `title` |
   | A transition between major parts, or a short section-opening statement | `section` |
   | A bulleted list of points, steps, or facts under one heading | `standard` |
   | Two things being compared, contrasted, or paired side by side | `two_column` |
   | A heading + short caption that belongs next to a picture | `image` |
   | One short, standalone, quotable statement with no supporting list | `quote` |

   If a section doesn't cleanly fit any of these six (e.g. it's really a stat callout, a process timeline, or a data table), **say so explicitly rather than forcing it into the nearest shape** — see "Known limitations" for the ~14 layout types not yet built; forcing e.g. a 4-step process into `standard` bullets loses the sequential/spatial meaning a real `steps`/`timeline` layout would carry. Cutting the section, merging it into an adjacent one, or flagging the gap to the user are all better than a bad-fit `layout` value.
3. **Render the template's slides to a thumbnail grid and look at it** (command below) — now that you know what shape each section needs, you're looking for a REAL template slide that matches, not browsing blind:
   ```bash
   .venv\Scripts\python.exe skills\slide-deck-composer\scripts\thumbnail_grid.py <template.pptx> <output_prefix> [--cols 4] [--per-grid 24]
   ```
   Writes `<output_prefix>_grid_1.jpg`, `_grid_2.jpg`, ... each cell labeled `slide_idx=N` (0-based, matches `prs.slides[N]` exactly). For each section from step 2, find a real slide whose visible structure matches: a `two_column` section wants a real slide with two side-by-side text blocks (a 2-icon "compare" slide, a pros/cons layout, etc.), not just any slide with 2+ body shapes on it — the grid shows you which ones actually look right, not just which ones would structurally pass `_fits()`'s checks.
4. **Write `content.json`, one entry per section, with the `layout` from step 2 and the `source_slide_idx` from step 3.** ONLY NOW write the actual markdown — and shape it to the chosen layout's real fields (a `two_column` slide's markdown needs two `###` sub-headings with their own bullet lists under each; a `quote`'s markdown is one line, not a paragraph — see the schema below). Content written before the layout was chosen tends to not map cleanly onto any layout's actual fields; content written for a specific already-chosen layout does.
5. **Compile.**
   ```bash
   .venv\Scripts\python.exe skills\slide-deck-composer\scripts\compile_deck.py <template.pptx> <content.json> <output.pptx> [--heading-font "Name"] [--body-font "Name"] [--vietnamese]
   ```
6. **Validate the real output structurally, and actually look at a render before calling it done** — this skill's own build history (10 real bugs across two rounds, see "Verified") is proof that a clean JSON report is not sufficient evidence on its own:
   ```bash
   .venv\Scripts\python.exe skills\slide-deck-composer\scripts\validate_deck.py <output.pptx> [--original <template.pptx>]
   ```
   If LibreOffice is available, render to PDF (`soffice --headless --convert-to pdf`) and inspect at least the slides `compile_deck.py`'s own JSON report flagged as `structural_match: false` or with unusually high `stale_text_shapes_cleared` counts, plus any slide `content_density.py` flags as unusually sparse (see below) — don't re-render every slide by default, that defeats the point of the triage tools. Also check the report's `repeated_source_slides` field (v0.8.0) — any `source_slide_idx` used for more than one output slide is listed there with its positions; a real 20-slide deck built without checking this reused the same section-divider design for 3 of 5 parts and the same bullet-slide design for 4 unrelated content slides, both visually monotonous and — for the divider case — factually misleading (see "Known limitations" on baked-in decorative ordinals).

Skipping steps 3-4's explicit `source_slide_idx` (omitting it on every slide) is a legitimate, still-fully-supported lower-effort fallback: `compile_deck.py` falls back to the automatic geometry-based heuristic exactly as before, unchanged, for any slide without an explicit index. Step 2's content-first classification still matters even on this fallback path — the heuristic can only pick a structurally-compatible slide for the `layout` you gave it, it cannot fix a `layout` choice that didn't match the content's real shape to begin with.

`content.json`:
```json
{
  "slides": [
    {"layout": "title", "markdown": "# Deck Title\nA subtitle line", "source_slide_idx": 0},
    {"layout": "standard", "markdown": "## Heading\n- bullet one\n- bullet two"},
    {"layout": "two_column", "markdown": "## Compare\n### Left\n- a\n### Right\n- b"},
    {"layout": "image", "markdown": "## Caption heading\nCaption body text",
     "image_path": "assets/photo.jpg"},
    {"layout": "image", "markdown": "## Placeholder example\nNo real photo yet",
     "generate_placeholder_image": true},
    {"layout": "quote", "markdown": "# \"A standalone statement.\""},
    {"layout": "section", "markdown": "## Section N\nSection subtitle"}
  ]
}
```

`layout` must be one of exactly these 6 keys (`compile_deck.py` refuses loudly, non-zero exit, on any other value — see "Known limitations" for the layout types not yet built). `--vietnamese` requires every font actually used (template theme fonts, or `--heading-font`/`--body-font` overrides) to have confirmed Vietnamese diacritic support; an unmapped font name is refused loudly rather than risking garbled diacritics.

`source_slide_idx` (optional int, any layout): explicitly clones `prs.slides[source_slide_idx]` for this output slide, bypassing the automatic heuristic. Still refused loudly (never silently guessed past) if the chosen slide genuinely lacks a scorable title shape or enough body shapes for the layout — and (v0.8.0) also refused if it has drastically MORE real body shapes than the layout uses, since that's a real signal the slide is actually several parallel content "cards" (e.g. a 3-column icon/stat slide) that a flat `standard`/`two_column`/etc. slot model will fill unevenly; the error message names `custom` as the right tool for that shape instead.

`image_path` / `generate_placeholder_image` (optional, `"image"` layout only): actually replace the cloned slide's real picture — a caller-supplied file, or (no `image_path` given) a deterministic no-network Pillow placeholder. A markdown `![alt](path)` reference in the slide's own `markdown` is honored as a fallback `image_path` source. Neither field set = the template's own original picture is left untouched (unchanged pre-v0.2.0 behavior).

Output is a JSON report on stdout: which real template slide was cloned for each output slide (and whether that choice was explicit or automatic), whether it was a structural match, how many stale template shapes were blanked, every font-size-balancing step actually applied, and (when an image was injected) the real injection report (frame size, whether letterboxing was applied, whether a pre-existing crop was cleared) — inspect this to confirm the compile did what you expect before trusting the `.pptx` blind, or run `validate_deck.py` for a mechanical check.

## Custom layout (v0.3.0) — the ad-hoc escape hatch, not a 7th special case

The 6 named layouts (`title`/`standard`/`two_column`/`image`/`quote`/`section`) will never cover every real template slide shape — Slidesgo/Canva/Google-Slides templates genuinely contain stat callouts, org charts, 3-column agendas, icon grids, budget breakdowns, and more, all with real, usable structure. Hardcoding a named layout for every one of those (the ~14 listed in "Known limitations") doesn't scale and re-litigates the same "which layout type is worth building" judgment call this project keeps having to make. **`"layout": "custom"` is the general answer**: the calling agent declares its own slot mapping for one specific real slide it already looked at (via `thumbnail_grid.py`), instead of Scriptorium trying to anticipate every possible template shape in advance.

```json
{"layout": "custom", "source_slide_idx": 10, "slots": [
  {"role": "title", "text": "63 skills"},
  {"role": "body", "text": "Registered in the Scriptorium skill catalog as of Aug 2026"}
]}
```

- **No automatic selection** — `source_slide_idx` is mandatory for `custom` (refused loudly if omitted). There's no generic content-pool to search heuristically for an ad-hoc shape; the caller already made the visual judgment call by looking at the thumbnail grid, so the tool trusts it rather than re-deriving it.
- **Positional matching, not named fields**: at most one `role: "title"` slot (matched to the slide's one scorable title shape), and `role: "body"` slots matched in the order written to the slide's scorable body shapes in `shape_roles`' own ranked (best-first) order. Count the slide's real distinct text areas from the thumbnail before writing `slots` — a mismatch (more slots than shapes, or a `title` slot on a slide with no scorable title) is refused loudly, never silently truncated or dropped.
- `text` as a plain string injects one line; as a list of strings, injects a bulleted list into that same shape — same underlying `_inject_single_line`/`_inject_bullets` primitives every named layout uses, so font-size balancing and Vietnamese font-safety both still apply per slot exactly as elsewhere.
- **This is deliberately NOT a promise to become a named layout later.** A shape recurring often enough across real decks to justify a purpose-built, validated content schema (the way `quote` gets a specific 1-slot contract with its own capacity rule) is a real signal to eventually build one — but `custom` staying available means that decision can wait for real recurring need instead of being guessed at upfront.

## The two owner-requested features (v0.1.x)

**1. Vietnamese font-safety checker** (`scripts/font_vietnamese.py`) — `check_font_vietnamese_safety(font_name)` reports `safe` / `substitute` (with a real same-category substitute) / `unknown` (refuses loudly — never guesses). Ported from a real, measured 35-font table (`FONT_METRICS` in the source's `layout_registry/font_config.py`), not invented. `compile_deck.py --vietnamese` wires this to BOTH the template's own theme fonts (read via `font_manager.FontManager`) and any caller-requested `--heading-font`/`--body-font` override, and writes the resolved font explicitly onto every run (`rich_text.apply_runs_to_paragraph`'s `base_font_name`) — not just the theme XML — so diacritic safety holds even for runs that would otherwise inherit an unsafe theme font.

**2. Content-length font-size balancing** (`scripts/font_size_balance.py`) — compares the just-cloned shape's ORIGINAL template text length against the caller's REPLACEMENT text length; every +50% over original length steps the font down one discrete tier (title: 4pt/step, floor 18pt; body: 2pt/step, floor 10pt; capped at 4 steps). Deterministic, not continuous scaling — see the module docstring for the full reasoning, including why the step unit is 50% (short version: `text_utils.enable_autofit`'s OOXML `normAutofit` already covers the 0–50% band at PowerPoint-open-time; this module pre-empts the harder cases with an explicit, predictable size instead of relying on one uniform autofit pass).

## Real picture injection (v0.2.0) — `scripts/image_injector.py`

Generalizes a real working prototype built earlier this session (`tests (ignore)/slide-deck-composer/swap_images.py`, a zip-level media-byte-swap proof of concept that never touches shape XML). That prototype's technique doesn't survive contact with `slide_duplicator.duplicate_slide`, though: `duplicate_slide` re-relates each cloned slide's picture to the SAME underlying image PART object (python-pptx's `relate_to(rel.target_part, ...)` does not duplicate media bytes), so a raw zip-level swap of `ppt/media/imageN.png` would silently overwrite that image for EVERY slide sharing it, not just the one being targeted. This module instead adds a genuinely NEW image part per replacement via `SlidePart.get_or_add_image_part`, so each slide's swap is independent.

**Granularity actually achieved (be honest about scope, not overclaiming)**: per-slide, single-picture. `image_injector.pick_best_picture` selects ONE top-level (non-grouped — same deliberate scope limit as `shape_roles.collect_text_shapes`) `Picture` shape per slide via `shape_roles.score_picture_shape` (largest/most-centered wins). A slide with multiple independently-addressable pictures is not supported this round — only the best-scoring one is replaced.

**Aspect-ratio handling actually achieved**: the replacement bitmap is letterboxed (padded, never stretched) to match the TARGET SHAPE's own frame aspect ratio (`shape.width/height` in EMU), and any pre-existing `<a:srcRect>` crop on the shape is explicitly removed — a crop rectangle authored against the OLD photo's pixels has no defined meaning against a brand-new image and would otherwise silently produce an arbitrary, wrong crop of the replacement. This is the "resize/letterbox to the frame's own aspect ratio" tier from this round's brief, not full crop-aware resizing against the original photo's own `srcRect` geometry.

**A real finding from this round's visual-review loop, investigated and resolved (not a defect in the end)**: the first real-template test (`Business Innovation Plan by Slidesgo.pptx`, source slide 13, a phone-mockup graphic) appeared UNCHANGED after injection when inspected at the `thumbnail_grid.py` default 480px-wide thumbnail resolution — alarming, since this skill's whole discipline is "don't trust a report, look at the render." Investigation (extracting the swapped media part directly, then re-rendering that one slide at 4x scale via `pypdfium2`) confirmed the swap WAS correct and visible — the target shape's frame is a narrow ~1.8in-wide sliver (a phone screen inside a larger illustration), so a thumbnail-grid cell for it is only ~65px wide, too small to distinguish a solid blue replacement photo's fine white border/caption text from the original's similarly-blue-toned sprite-sheet crop at a glance. Real lesson banked for future visual-review rounds: `thumbnail_grid.py`'s default resolution is right for SLIDE-level layout judgment (which template slide fits which content), not for verifying a small shape's exact pixel content — that needs a targeted higher-resolution single-slide render, which `thumbnail_grid.py`'s `pdf_to_thumbnails(width_px=...)` already supports as a parameter for exactly this case.

## Content-density triage (v0.2.1) — `scripts/content_density.py`

A fast, deterministic pre-filter over a rendered deck: grid-scans every slide for near-empty (low edge-density) regions and reports which slides are worth spending an actual image-read on, instead of an agent visually inspecting every slide of a 40+-slide deck to find the sparse ones. Owner-proposed idea, prototyped and validated on a real slide before being built into the skill (see the two-round experiment below).

**Explicitly a triage tool, not a judge**: `flagged_for_review` means "worth a closer look," never "defective" — a large empty region can be intentional whitespace (this skill's own "Zero-noise delivery" example slide is deliberately spacious and still good design). The script reports an empty-percentage and a concrete bounding box (`largest_empty_rect`, as a 0-1 fraction of slide width/height); whether to add content, leave it, or place an image there is entirely the calling agent's judgment — matching this whole skill's "infrastructure + context, not a gate" architecture.

**Technique, and why the obvious first approach was wrong**: a naive per-grid-cell PIXEL-VARIANCE scan was tried first and rejected — it false-flagged flat-color illustration blocks (the dominant style in real Slidesgo templates) as "empty," since each flat-color region inside an illustration is locally uniform on its own. Real test on `scriptorium_intro_v7.pptx`'s title slide: 177/256 cells wrongly flagged, including most of the illustration. Switching to EDGE DENSITY (PIL's `FIND_EDGES` kernel, mean edge intensity per cell) fixed it — a color boundary still produces edge signal even inside a uniformly-colored illustration block, so it correctly tells "flat-colored content" apart from "genuinely blank background." Re-verified on the same slide: the illustration area correctly excluded from the empty mask, the actual blank background correctly flagged.

Largest-empty-rectangle uses the standard histogram + monotonic-stack algorithm over the boolean empty-cell grid (O(rows·cols)), giving one concrete bounding box per slide rather than just a scattered percentage.

## Known limitations

- **6 named layouts + 1 general escape hatch**: `title`, `standard` (bullets), `two_column`, `image`, `quote`, `section`, plus `custom` (v0.3.0, see "Custom layout" above) for any real template shape the 6 named ones don't cover — `three_column`, `table`, `timeline`, `stat`, `pros_cons`, `steps`, `icon_grid`, and similar are all reachable today via `custom`, not blocked pending a dedicated layout. `code`/`chart`/`diagram`/`qa`/`center_generic`/`end_card`/`fullbleed_image` are reachable the same way for their TEXT content, but `custom` only injects text into scored title/body shapes — a slide whose real content is a native chart object, an embedded code block with syntax highlighting, or a picture-only full-bleed layout still isn't meaningfully served by text-slot injection alone. `shape_roles`' icon-grid/infographic DETECTION logic (`_MAX_BODY_SHAPES_FOR_PROSE`, `max_unused_body_shapes`) from v0.1.1 remains real and proven — a future round promoting `stat`/`icon_grid` from `custom` usage to a purpose-built named layout (once real recurring need justifies the dedicated content schema + capacity rule a named layout gets) starts from that solid, already-verified detection base.
- **`image` layout picture injection (v0.2.0) is real but single-picture-per-slide granularity** — see "Real picture injection" above for exactly what was and wasn't built (per-slide best-picture selection via `shape_roles.score_picture_shape`, frame-aspect-ratio letterboxing + crop clearing, not full crop-aware resizing against the original photo's own `srcRect`). A slide with multiple independently-addressable pictures only gets its single best-scoring one replaced. `scripts/image_formatter.py` (rounded-corner/border/shadow finishing on an already-inserted picture) remains implemented and independently testable but still not wired into `compile_deck.py` — a natural follow-up now that real injection exists to finish on top of.
- **Grouped shapes are now supported (v0.4.0)** — `shape_roles.iter_shapes_with_absolute_bbox` recurses into `<p:grpSp>` groups at any nesting depth and correctly maps each leaf shape's bounding box through however many group transforms sit above it (handles both identity transforms, the common case in the real templates checked, and non-identity scale/offset transforms). Text and pictures nested inside a group are real, scorable title/body/image candidates now, same as top-level shapes — see "Verified" for a real grouped-text and a real grouped-picture injection, both rendered and visually confirmed correctly positioned. Still NOT addressed: a group containing dozens of near-empty decorative sub-shapes (common — real vector illustrations are frequently built from many small AutoShapes with unused text frames) relies entirely on the existing `is_decorative_text` filter to stay out of scoring; that filter was already proven correct against exactly this case (a 60-child-shape illustration group, zero false positives) but hasn't been stress-tested against every possible decorative-group shape, only the real templates checked this round.
- **`thumbnail_grid.py` requires a real LibreOffice install** (`soffice`) — the only script in this skill with an external-binary dependency; every other script (including `compile_deck.py` itself) remains subprocess-free. If `soffice` isn't installed, the recommended agent-driven-selection workflow degrades gracefully to the automatic-heuristic fallback (still fully functional), just without the visual-picking step.
- **No auto-pagination.** If real content is far too long to fit even after font-size balancing, this skill does not automatically split it across additional slides (the source system's `split_content_for_pagination` was deliberately not ported — out of scope). `text_utils.truncate_text`'s hard character limits are the only backstop against runaway text.
- **No `--vietnamese` auto-detection.** The flag must be passed explicitly by the caller; content containing Vietnamese diacritics compiled without `--vietnamese` will use whatever font the template/caller specifies, safe or not.
- **`--vietnamese`'s per-shape font resolution (v0.6.0) is best-effort, not a full OOXML style-cascade resolver.** `font_manager.resolve_effective_font` checks (in order) a shape's own explicit run-level font, then its matching slide-layout placeholder's `<a:lstStyle>/<a:lvl1pPr>/<a:defRPr>/<a:latin>`, then the slide master's `<p:txStyles>` (`titleStyle`/`bodyStyle`/`otherStyle`) — this covers every real case found in the templates checked this session, but does NOT walk per-paragraph `lvl2pPr`..`lvl9pPr` overrides, does not reconcile a layout placeholder that only PARTIALLY overrides the master (mixing tiers), and does not handle a shape whose real font comes from a still-deeper/unusual inheritance path. Falls back to the theme scheme (the old, only, behavior) when none of the three tiers has an explicit font — never worse than before, but not a guaranteed-complete cascade.
- **`font_vietnamese._FONT_TABLE` is keyed on the exact run-level font NAME string, including weight suffixes** (e.g. `"Schibsted Grotesk"` and `"Schibsted Grotesk Medium"` are two separate table entries, even though they're the same font family with the same real Unicode glyph coverage). Found via v0.8.1's real dogfooding round: a single real template used 2 weight variants of the same family across different shapes, requiring 2 near-duplicate table entries to fully clear `--vietnamese`. Not normalized this round (the exact-match design is deliberate -- "never guess" -- and a naive suffix-stripping heuristic risks silently matching an unrelated font that merely shares a name prefix); a future round could add a real, verified weight-suffix-aware lookup if this keeps recurring across more templates.
- Not yet tested against templates with embedded charts, SmartArt, or video — `slide_duplicator.duplicate_slide` clones their XML/relationships generically (the same rId-remap logic that handles pictures) but this was not specifically exercised in this round's real-template tests either.
- **P2 items (font QA-reliability tagging, `references/design-guidance.md`) were not attempted this round** — explicitly out of scope given the P0/P1 time budget; not started, not partially started, nothing to report.
- **A source slide's own baked-in decorative ordinal/numeral (e.g. a section-divider's "01" badge) does not update when that same slide is reused for a differently-numbered section.** Found via v0.8.0's real 20-slide dogfooding round: a section-divider template slide whose decorative badge literally reads "01" got reused (by explicit `source_slide_idx`, the recommended workflow) for "Part V" of a 5-part deck, leaving a real, visible factual mismatch ("01" next to "Phần V"). This is a direct, unavoidable consequence of `is_decorative_text`'s digit-only-text rule correctly treating short numerals as immutable design content (the same rule that correctly protects real stat-callout badges like "$4.5B" or "271K" from being blanked or overwritten) -- there's no reliable way to distinguish "this numeral is a meaningful section ordinal that must track reuse" from "this numeral is a decorative design flourish with no semantic meaning" from geometry or text content alone. Not code-fixed: forcibly making short decorative numerals editable would reopen exactly the false-positive class that rule exists to prevent. Mitigation is a caller-side judgment call, not an engine guarantee: if a template's section-divider slide has a baked-in ordinal, either use a different divider design per part (if the template offers more than one), fold the part number into the caller-supplied title text instead of relying on the template's own badge, or accept that the badge won't track reuse.
- **Reusing the same source slide across several unrelated positions is possible and sometimes correct, but not automatically flagged as a visual-monotony risk beyond the report field added in v0.8.0.** `compile_deck.py`'s JSON report's `repeated_source_slides` field lists every `source_slide_idx` used more than once (with its positions and count) so a caller can check for unintentional repetition, but nothing refuses or warns during compile itself -- a caller (or reviewing agent) has to actually read that report field. See "Usage" for the recommended workflow.
- **Dense multi-widget "dashboard" templates (every real slide built from many small separate chart/table/callout shapes, no plain bullet or pull-quote slide anywhere) are a genuine structural mismatch for the generic named layouts.** Found via v0.7.1's real dogfooding round against `Data Infographics by Slidesgo.pptx`: `two_column`/`section` against such a template correctly blank sibling body regions the caller's content didn't fill (a colored box with no text — not a leaked-text bug, just visually incomplete) whenever the source slide has more discrete regions than the layout's content model assumes; `quote` leaves the source slide's own background chart/table visible behind the quote text, since clone-and-inject deliberately preserves a source slide's own graphic elements rather than stripping them. Not code-fixed, because the correct answer already exists: use `custom` with an exact slot count for this class of template (verified clean in the same round — 2 of 7 showcase slides used `custom` with zero visual defects). A future round could consider auto-detecting this template shape and steering the caller toward `custom`, but that's a UX nicety, not a defect.
- Hasn't gone through stage 4 (formal multi-harness quality eval) — per this project's `CLAUDE.md`, this is a deliberate hold on the formal scoring gate, not a statement about implementation quality; security-audit self-check passed (see above), and 16 real bugs across six rounds (5 structural, 5 visual-review, 3 dogfooding, 1 cardinality-mismatch, 2 v2-dogfooding) plus real image-injection/thumbnail-grid/cold-agent/schema-validation verification have been found/fixed/confirmed against real adversarial template content.

## What this skill does NOT do

- Does not invent visual design, layout geometry, or color choices from scratch — see "Architecture decision" above. If the caller has no template, use `office-doc-creator`'s flat pptx path instead.
- Does not download, embed, or manage fonts (Google Fonts fetch, font embedding) — `font_engine.set_theme_fonts` only rewrites the theme XML's font *name* reference; if that font isn't installed on the machine that later opens the file, PowerPoint substitutes its own fallback, same as any `.pptx`.
- Does not call any AI/image-generation backend — per this project's `CLAUDE.md` principle 8, Scriptorium never integrates an AI API. Picture content is the template's own original image (untouched, when no `image_path`/`generate_placeholder_image` is given), a caller-supplied real file, a deterministic Pillow placeholder, or something a caller-side skill (e.g. `image-generator-gemini`) generates and hands over as a file path.
- Does not verify or fact-check the caller-supplied content — this is a rendering/injection engine, not a research or grounding tool (pair with `deep-research`/`literature-review`/`citation-management` upstream if factual grounding is required).
- Does not read/analyze an existing presentation — that's `document-ai-structurer`'s job.
- `compile_deck.py` itself still does not convert to PDF or render a preview image — the compile contract ends at a valid `.pptx` file. `thumbnail_grid.py` (v0.2.0) is a deliberate, separate, opt-in tool that DOES call a real `libreoffice` subprocess (fixed argument list, no `shell=True`, documented in "Security & isolation self-check") specifically to render a template's slides for agent-driven selection — this is a scoped exception to the prior round's "no shell-out by default" stance, not a reversal of it: the compile pipeline's own security posture is unchanged, and the one new subprocess call is isolated to a single opt-in script.

## Composability

- **`image-generator-gemini`** (BYOK image generation): now a real, wired filler for the `image` layout's picture slot (v0.2.0) — the calling agent generates an image via that skill, then passes the resulting file path as `content.json`'s `image_path` (or a markdown `![alt](path)` reference); `compile_deck.py`'s `LAYOUT_IMG` branch calls `image_injector.inject_slide_image` to swap it in for real, letterboxed to the target shape's frame aspect ratio. Verified this round with a real Pillow-generated test file standing in for `image-generator-gemini`'s actual output (same file-path contract, no live chaining test run since that would require actually invoking the other skill).
- **`deep-research` / `literature-review` / `citation-management`**: their findings/summaries are natural sources for a `content.json`'s markdown bullets — this skill takes already-written content, not raw research.
- **`personal-profile-manager`**'s `org_profile` section (org name/logo): natural source for a title slide's subtitle line or a caption on a closing slide — this skill has no org-identity concept of its own, it only injects whatever text the caller supplies.
- **`office-doc-creator`**: sibling document-creation skill, **no scope overlap** — `office-doc-creator`'s pptx path is flat title/bullet-only with no template support; this skill is the real template-clone engine for when a caller has (or is given) an actual designer template.
- **`light-logo-arranger`**'s `scripts/resolve_font_fallback.py`: `font_vietnamese.py`'s refuse-rather-than-guess pattern is the same discipline, applied to a different question (Vietnamese diacritic support vs. geometric font substitution) — read together, they're two instances of one project-wide convention: never silently guess a font behaves a way it hasn't been verified to behave.
- **`content_density.py` → `thumbnail_grid.py` → `image-generator-gemini`**: a natural triage-then-act chain within this skill itself. Run `content_density.py` on a compiled deck to cheaply flag which slides have a large empty region worth a second look (instead of visually inspecting every slide), then for a flagged slide, use `thumbnail_grid.py`/a targeted render to actually look at it, then decide whether to fill it via `image-generator-gemini` + `image_injector.py`, add more content, or leave it (intentional whitespace is a valid outcome `content_density.py` cannot and does not judge on its own).
